# Codex Prompt — Build the StoryBook-Test Agent System

You are GPT-5.6 Sol Medium working inside the `StoryBook-Test` repository.

Your task is to create a complete, context-efficient agent system for migrating Angular 16 components from a separate legacy Angular application into this repository for high-fidelity Storybook + Playwright performance/stress testing.

The system you create will later be executed mainly by an OpenCode implementer model with a context window of approximately 100K tokens.

Therefore:

> CONTEXT EFFICIENCY IS A FIRST-CLASS ARCHITECTURAL REQUIREMENT.

The final agent system must be designed so that the implementer model reads only the instructions and artifacts required for the current migration stage.

Do NOT create a giant globally-loaded agent instruction set.

## 1. Core Operating Model

The migration process is sequential.

I will manually invoke one MAIN AGENT at a time.

Example:

```text
Project Bootstrap Agent
↓
Source Analysis Agent
↓
Migration Planning Agent
↓
Component Scaffold Agent
↓
Component Tree Migration Agent
↓
Data Agent
↓
Harness Agent
↓
Benchmark Integration Agent
↓
Test Agent
↓
Fidelity Validation Agent
↓
Repair Agent when necessary
```

A MAIN AGENT is a migration stage.

A SUB-AGENT is a narrow implementation worker owned by the currently running MAIN AGENT.

The system must NOT act like one large autonomous agent that migrates the entire component in one run.

Expected flow:

```text
Human invokes Main Agent A
    ↓
Main Agent A loads minimum required context
    ↓
Main Agent A delegates selected tasks to sub-agents
    ↓
Main Agent A integrates their work
    ↓
Main Agent A validates its own stage
    ↓
Main Agent A writes compact artifacts + handoff
    ↓
Main Agent A stops

Human invokes Main Agent B
    ↓
Main Agent B loads only what it needs
```

Each stage must be independently resumable.

Core rule:

> DISCOVER TOP-DOWN. IMPLEMENT BOTTOM-UP.

The component tree is analyzed from parent to child, but creation/adaptation is performed from deepest child to root using post-order traversal.

Example source tree:

```text
Root
├── ChildA
│   └── GrandchildA1
└── ChildB
```

Discovery order is conceptually:

```text
Root
→ ChildA
→ GrandchildA1
→ ChildB
```

Preferred implementation order is:

```text
GrandchildA1
→ ChildA
→ ChildB
→ Root
```

The root component is migrated last.

For EACH component node:

```text
1. Copy the source implementation faithfully.
2. Copy/adapt its template.
3. Copy/adapt its styles.
4. Ensure required migrated child components already exist.
5. Adapt production dependencies according to the migration plan.
6. Establish the migrated component's stable inputs/outputs/local-state contract.
7. Compile/verify that node.
8. Record deviations.
9. Only then move upward to its parent.
```

A parent must not be finalized before all required migrated children expose stable migrated contracts.

Preserve whenever possible:

- HTML/template structure
- DOM structure
- Less/CSS
- class names
- child component composition
- pipes/directives
- rendering calculations

service-loaded data -> @Input()

## Mandatory Component Traversal Invariant

This is a hard migration rule.

### Discovery / Scanning Order

Scanning MUST happen from parent to child.

Start from the requested top-level benchmark target and recursively discover rendered descendants and their dependencies.

The scanner must preserve:

```text
parent-child relationships
depth
shared descendants
conditional children
dependency relationships
```

This top-down scan is necessary because the parent determines which children are actually part of the rendering workload.

### Creation / Adaptation Order

Creation MUST happen from child to parent.

Use a post-order traversal.

For:

```text
Root
├── ChildA
│   └── GrandchildA1
└── ChildB
```

the implementation order should be:

```text
GrandchildA1
→ ChildA
→ ChildB
→ Root
```

A migrated parent should consume already-migrated child contracts.

### Adapt During Creation

Do not perform:

```text
copy entire tree
then later dumbify entire tree
```

Instead perform:

```text
copy child
→ adapt child
→ compile child
→ move to parent
```

Each component must be converted at the point it is created.

Examples:

```text
this.store.select(...) -> @Input()
store.dispatch(...) -> @Output()
service-loaded data -> @Input()
router state -> @Input()
application side effect -> emitted event / harness action
```

### Why

This improves:

- context efficiency
- correctness of parent contracts
- compile-time locality
- fault isolation
- reuse of already-adapted children
- stability with a ~100K-context implementer model

The root/top-level benchmark component is always created last.
